# إضافة DSHRSI: التحسين الذاتي التكراري (Recursive Self-Improvement) لـ DeepSeek Harness

### **راقِب ← حسِّن ← ابنِ على التحسين ← ثم من جديد. harness يصير لك أنت أكثر فأكثر.**

**يرمز RSI إلى Recursive Self-Improvement، أي التحسين الذاتي التكراري؛ أما DSHRSI فهو الإضافة (plugin) مفتوحة المصدر التي تجعله واقعًا في DeepSeek Harness. الـ harness (الكود الذي يشغّل النموذج وأدواته) يراقب تشغيلاته هو نفسه، ويجعل نموذج الجلسة نفسها يكتب كود harness لما يجده من مشكلات، ويثبت صحة ذلك الكود في بوابة تحقق من 5 مراحل، ثم يركّبه قبل أن تنتهي الجولة. بعدها يتولى الـ harness المحسَّن الجلسة التالية، ويتحسّن من جديد. بلا ضبط دقيق للنموذج (fine-tuning). وبلا أكوام من الموجّهات (prompts). بل كود يُقاس، فيُحتفظ به أو تُعاد كتابته أو يُرمى.**

<a id="rsi"></a>

## 🔁 التحسين الذاتي التكراري: RSI = Recursive Self-Improvement

ليس المقصود "rewrite itself"، أي أن يعيد كتابة نفسه. بل **التحسين الذاتي التكراري**: نظام يستخدم قدراته هو ليحسّن نفسه، ثم يتولى النظام المحسَّن الدورة التالية. ثلاث كلمات، وعلى DSHRSI أن يستحق كل واحدة منها:

| | المطلوب | كيف يحققه DSHRSI |
| :--- | :--- | :--- |
| **الذاتي (Self)** | مَن يغيِّر ومَن يتغيَّر نظام واحد | الـ harness يغيّر الـ harness. والتكييف يكتبه نموذج الجلسة نفسها التي اصطدمت بالمشكلة. لا أحد يضبطه من الخارج |
| **التحسين (Improvement)** | يجب أن يكون "الأفضل" قابلًا للفحص | كل تكييف يجتاز بوابة من 5 مراحل قبل تركيبه، ثم تختبره الجلسات اللاحقة من جديد: ما ينفع يُرقّى، وما يرمي خطأً يُعزل |
| **التكراري (Recursive)** | مخرجات كل دورة هي بداية الدورة التي تليها | الجلسة التالية تعمل على الـ harness المحسَّن وتُراقَب وهي تعمل عليه. التكييف الذي لم يصمد تُعاد كتابته بصرامة أشد استنادًا إلى الأدلة. والتكييف الذي تحتاج إليه مساحة عمل ثانية يتّسع ليشمل الجهاز كله، وقواعد المشروع تنتقل إلى الـ harness عند كل زميل في الفريق |

**أربع حلقات، كل واحدة داخل التي تليها:** داخل الجولة الواحدة ← من جلسة إلى جلسة ← التحسين نفسه يُحسَّن ← من المشروع إلى الجهاز إلى الفريق.

ما **لا** يشمله التكرار عن قصد: أوزان النموذج لا تتغير أبدًا، والكواشف وسياسة التفعيل وبوابة التحقق كود ثابت لا يستطيع أي تكييف أن يمسّه. الجزء الذي يعدّل نفسه يفحصه جزء لا يملك أن يعدّله.

<a id="quick-start"></a>

## ⚡ البداية السريعة في 30 ثانية

### 1. ثبّته حيث تعمل أصلًا
في تطبيق سطح المكتب لـ DeepSeek Harness أو في واجهة الويب، افتح **Plugins → Add plugin → Install a third-party plugin**، والصق رابط حزمة الإصدار، ثم اختر **Install** وبعدها **Enable now**:

```text
https://github.com/qybaihe/dshrsi/releases/download/v0.1.2/dsh-rsi-0.1.2.tgz
```

أو من سطر الأوامر. لكل profile (ملف تعريف) إضافاته الخاصة، والأمر `dsh plugin add` يستدعي `pnpm`، فيجب أن يكون موجودًا في `PATH`:

```bash
dsh plugin --profile web add https://github.com/qybaihe/dshrsi/releases/download/v0.1.2/dsh-rsi-0.1.2.tgz
dsh web
```

### 2. اعمل كعادتك
لا شيء يحتاج إلى إعداد. يبقى DSHRSI بعيدًا عن الأنظار إلى أن تعود المشكلة نفسها. عندها تضيء شارة **RSI**، وتخبرك كبسولة الحالة تحت حقل الكتابة أن الـ harness غيّر نفسه للتو، وتبدأ الجلسة التالية وهي محسَّنة سلفًا:

<div align="center">
<img src="../../assets/ui-panel-dark.png" alt="الجلسة التالية: الكبسولة مفتوحة وتعرض التكييف العامل والاستدعاء الذي رفضه قبل أن يُنفَّذ" width="1200" />
</div>

اكتب `/rsi` في أي جلسة لترى ما هو مركَّب، وإلى أي طبقة ينتمي، وما الذي ينتظر موافقتك.

### 3. امنح المستودع harness خاصًّا به
القواعد المكتسبة داخل مستودع يمكن أن تعيش في ذلك المستودع نفسه، ملف واحد لكل تكييف:

```bash
# يأتي هذا الأمر مع الإضافة، داخل الـ profile الذي ثُبّتت فيه
alias dsh-rsi="$HOME/.dsh/profiles/web/node_modules/.bin/dsh-rsi"

dsh-rsi project init      # داخل المستودع: ينشئ .dsh-rsi/، ثم أضِفه في commit
dsh-rsi trust             # على كل جهاز آخر: اقبل الملفات بعد قراءتها
```

### 4. التشغيل من المصدر

```bash
git clone https://github.com/qybaihe/dshrsi.git && cd dshrsi
npm install               # يجلب نسخة dsh مثبَّتة الإصدار ومعها pnpm الذي تستدعيه
npx dsh plugin --profile web add "$PWD/packages/dsh-rsi"
npx dsh web
```

شرح الـ profiles `desktop` و`headless`، وفهارس الإضافات، وملفات tarball المحلية، والتحميل لتشغيل واحد فقط، كله في [مرجع الإضافة](../../packages/dsh-rsi/README.md#install).

## 🧠 كيف يعمل DSHRSI: حلقة مغلقة داخل الـ harness، تدور مرة بعد مرة

<div align="center">
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="../../assets/pit-stop.dark.svg" />
  <img src="../../assets/pit-stop.svg" alt="طريقة عمل DSHRSI مرسومة كتوقف في منطقة الصيانة: السيارة هي الـ harness، والسائق هو النموذج، والقطعة الجديدة هي كود للـ harness كُتب في منتصف الدور" width="960" />
</picture>
</div>

الـ skills وملفات الذاكرة وموجّهات النظام (system prompts) الأطول تعمل كلها على مستوى السياق: تضيف نصًّا وتأمل أن يتبعه النموذج. وحين لا يتبعه، يتكرر الاستدعاء الفاشل نفسه في الجلسة التالية.

**أما DSHRSI فيعمل على مستوى الـ harness. ما يتعلمه يصير كودًا على نقاط التوسعة (extension points) في الـ harness نفسه:**

```mermaid
flowchart LR
  subgraph S1["1 · المراقبة"]
    A["أحداث الجلسة"] --> B["16 كاشفًا"]
  end
  subgraph S2["2 · القرار"]
    B --> C["بصمة الاحتكاك<br/>+ المكتبة + الجلسات السابقة"]
  end
  subgraph S3["3 · إعادة الكتابة"]
    C --> D["نموذج الجلسة<br/>يكتب تكييفًا"]
    D --> E["بوابة تحقق من 5 مراحل"]
    E -. "مرفوض، مع الأسباب" .-> D
  end
  subgraph S4["4 · التركيب"]
    E --> F["سياق node:vm معزول<br/>يعمل قبل طلب النموذج التالي"]
  end
  subgraph S5["5 · الحفظ والمشاركة"]
    F --> G["المكتبة: ترقية · عزل · تنقيح"]
    G --> H[".dsh-rsi/ في المستودع"]
  end
  G -. "من هنا تبدأ الجلسة التالية" .-> A
```

| المرحلة | الآلية | الأثر |
| :--- | :--- | :--- |
| **1. المراقبة** | تقرأ الكواشف الـ 16 أحداث الجلسة بعد توحيد صيغتها: استدعاءات تفشل من جديد، وأسباب فشل تعود مرة بعد مرة، وتخبّط في الأوامر، وتصحيحات من المستخدم، وجولات تنتهي دون التحقق من أي شيء | تأخذ المشكلة بصمة ثابتة عبر الجلسات، مثل `bash:command-not-found:python` |
| **2. إعادة الكتابة** | نموذج الجلسة نفسه يكتب تكييفًا بلغة JavaScript وفق API من 10 قدرات. الكود المرفوض يعود إليه مع الأسباب، مرتين على الأكثر، ثم يتولى الأمر قالب مدمج جاهز | الإصلاح كود في الـ harness، لا فقرة أخرى تُضاف إلى الموجّه |
| **3. التحقق** | فحص ساكن ← تحميل ← إعادة تمثيل ← اختبار انحدار ← صلاحيات. على التكييف أن يتصرف إزاء الاستدعاءات التي تسبّبت في كتابته، وأن يترك كل استدعاء نجح في هذه الجلسة على حاله | الكود الذي لا يفعل شيئًا، أو يكسر ما كان يعمل، لا يُركَّب أبدًا |
| **4. التركيب** | يعمل التكييف في سياق `node:vm` خاص به خلف جسر JSON، مع مهلة زمنية لكل استدعاء، ويسري مفعوله قبل طلب النموذج التالي | الجولة التي اصطدمت بالمشكلة هي أول من يستفيد |
| **5. الحفظ والمشاركة** | مكتبة لكل جهاز، معها سجلّ حركات (ledger) وسجلّ تدقيق. ما ينفع يُرقّى، وما يرمي خطأً يُعزل، وما لم يصمد تُعاد كتابته بصرامة أشد، وقواعد المشروع تُكتب في `.dsh-rsi/` | الجلسة التالية تبدأ وهي متكيّفة، وزملاء الفريق يحصلون على قواعد المشروع بعد `dsh-rsi trust` |
| **↻ من جديد** | الجلسة التالية تعمل على الـ harness الذي خلّفته المرحلة 5، والمرحلة 1 تراقبها وكل التكييفات في مكانها | تحسين يُبنى على تحسين. هذا هو التكرار (recursion) |

## 🔬 قياس على نموذج حقيقي

هذه الأرقام ناتجة عن تشغيل نموذج حقيقي، `mimo-v2.6-pro`، في جلسات `dsh` حقيقية (`npm run test:live`). لا شيء في هذا الجدول محاكاة.

> **كيف تقرأ هذا:** العيّنة صغيرة. نموذج واحد، وثلاثة سيناريوهات، وبضع جلسات لكل منها. هي تُظهر أن الحلقة تعمل من أولها إلى آخرها. لكنها **ليست** حكمًا إحصائيًّا على معدلات النجاح، ولم يصبح شيء أسرع: كتابة التكييف تنتظر النموذج 30–60 ثانية. التشغيلات الأكبر في قسم [اختبارات الـ benchmark](#benchmarks).

| السيناريو | بدون DSHRSI | مع DSHRSI | ما كتبه الـ harness |
| :--- | :--- | :--- | :--- |
| **أمر مفقود**: ملف README يقول `python stats.py`، والجهاز ليس فيه إلا `python3` | ❌ **5 / 5** جلسات نفّذت الاستدعاء الفاشل | ✅ **0 / 7** جلسات بعد التكييف (9 / 9 قبله) | `deny` + `prompt`، كتبهما النموذج، واجتازا البوابة من المحاولة الأولى |
| **قاعدة ذكرها المستخدم مرة واحدة**: "لا تعدّل `notes.txt` أبدًا، واكتب في `notes.draft.txt`" | ❌ الجلسة التالية عدّلت `notes.txt` | ✅ الجلسة التالية كتبت في `notes.draft.txt` دون تذكير | `deny` + `prompt`، كتبهما النموذج مباشرة بعد التصحيح |
| **إصلاح لم يطلب أحد التحقق منه** | لم يُشغَّل | ⚪ لم يُكتب شيء: النموذج تحقق من إصلاحه في 3 / 3 جلسات، فلم يكن هناك ما يُتعلَّم | لا شيء |

شُغِّل السيناريو الأول ثلاث مرات مع الإضافة، كل مرة من مكتبة فارغة، ومعها تشغيل ضابط واحد. وشُغِّل الثاني مرة معها ومرة بدونها.

**الأمر المفقود، جلسةً بجلسة** (عدد استدعاءات الأدوات الفاشلة في كل جلسة):

| التشغيل | S1 | S2 | S3 | S4 | S5 | S6 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **بدون DSHRSI** | ❌ 1 | ❌ 1 | ❌ 1 | ❌ 1 | ❌ 1 | |
| **مع DSHRSI · التشغيل 1** | ❌ 1 | ❌ 1 | ❌ 1 → 🧬 | ✅ 0 | ✅ 0 | ✅ 0 |
| **مع DSHRSI · التشغيل 2** | ❌ 1 | ❌ 1 | ❌ 1 → 🧬 | ✅ 0 | ✅ 0 | |
| **مع DSHRSI · التشغيل 3** | ❌ 1 | ❌ 1 | ❌ 1 → 🧬 | ✅ 0 | ✅ 0 | |

🧬 يشير إلى الجولة التي كتب فيها النموذج التكييف وركّبه الـ harness. في 3 من الجلسات الـ 7 التي تلته، ظل النموذج يحاول `python`، فرفض الـ harness الاستدعاء قبل تنفيذه. كل جلسات هذا السيناريو انتهت بالإجابة الصحيحة، مع الإضافة أو بدونها.

لإعادة التجربة محليًّا:

```bash
MIMO_API_KEY=... npm run test:live -- python --sessions 6          # مع الإضافة
MIMO_API_KEY=... npm run test:live -- python --sessions 5 --off    # تشغيل ضابط بدونها
```

## 🧩 ثلاث طبقات، ولكل مشروع harness خاص به

كل تكييف ينتمي إلى واحدة من ثلاث طبقات. ويمكن إيقاف كل طبقة على حدة:

| الطبقة | ما تحتويه | مثال | أين تُطبَّق |
| :--- | :--- | :--- | :--- |
| **`machine`** | حقائق عن هذا الحاسوب | لا يوجد `python`؛ منفذ مشغول؛ اسم مضيف داخلي لا يُحَلّ | مساحة العمل التي اكتُسب فيها، ثم الجهاز كله حالما تصطدم به مساحة عمل ثانية |
| **`user`** | كيف تحب أن تُعامَل | ردّ قُيِّم بأنه سيئ وكُتب "طويل جدًّا" سببًا لذلك | الجهاز كله |
| **`project`** | قواعد مستودع بعينه وعاداته | "هذا المستودع يستخدم pnpm دائمًا" | مساحة العمل، والمستودع نفسه عبر `.dsh-rsi/` |

**طبقة المشروع تسافر مع الكود:**

```
.dsh-rsi/
  harness.json           علامة الصيغة وإعدادات على مستوى المشروع
  adaptations/
    remember-the-user-s-instruction-3f2a1c.js     تكييف اكتُسب ثم كُتب هنا
    no-force-push.js                              والمكتوب يدويًّا يعمل بالطريقة نفسها
```

- **أضِف الملف في commit لتشاركه، واحذفه لتفصله.** الملف الواحد تكييف واحد.
- **لا شيء يعمل لمجرد أنك نسخت المستودع (clone).** كل جهاز يقبل المحتوى الحرفي للملفات عبر `dsh-rsi trust`، ويقبلها من جديد كلما تغيّرت.
- **المشروع لا يستطيع إلا أن يجعل الـ harness أكثر تحفظًا**، لا أقل. وإعدادات مثل `autonomy` خارج متناول المشروع.
- **قابل للنقل خارج المستودع أيضًا.** الأمران `dsh-rsi export` و`dsh-rsi import` ينقلان طبقتي الجهاز والمستخدم إلى حاسوب آخر في ملف واحد.

<a id="security"></a>

## 🔒 الأمان والإعدادات الافتراضية

- **فئة تلقائية لا تملك إلا التشديد** — دون موافقتك، لا يستطيع التكييف إلا أن يضيف معلومة أو يرفض أو يسأل أو يشترط التحقق. و`deny` و`ask` عنده لا يملكان إلا جعل حكم السياسات الأخرى أشد صرامة.
- **الموافقة شرط للقوة (`autonomy: tighten`)** — التكييفات التي تعيد كتابة النتائج أو تضيف أدوات أو تشغّل أوامر تُخزَّن بحالة `proposed` وتنتظر `dsh-rsi approve <id>`.
- **غير مرئي حتى تحتاج إليه** — حين لا يوجد احتكاك (friction) ولا شيء مركَّب، يبقى موجّه النظام وقائمة الأدوات والرسائل بلا تغيير، بايتًا ببايت. وهناك اختبار شامل يحرس ذلك.
- **أعطال محصورة** — المعالج (handler) الذي يرمي خطأً لا يؤثر أبدًا في استدعاء الأداة المرتبط به. وبعد ثلاثة أخطاء يُعزل التكييف.
- **كل شيء مدوَّن** — كل قرار في `audit.jsonl`، وكل احتكاك وتركيب وإجراء في `ledger.jsonl`. والأوامر `dsh-rsi disable` و`retire` و`rollback` تسحب التكييف أو تعيده إلى ما قبله.
- **ثلاثة أوضاع** — الوضع `adapt` يركّب مباشرة (وهو الافتراضي)، و`propose` يولّد وينتظرك، و`observe` يسجّل فقط.

<a id="faq"></a>

## ❓ الأسئلة الشائعة

<details>
<summary><strong>هل يضبط DSHRSI النموذج ضبطًا دقيقًا (fine-tuning) أو يغيّره؟</strong></summary>

لا. أوزان النموذج لا تُمسّ ولا يُدرَّب شيء. الذي يتغير هو الـ harness: الكود الذي يعمل حول موجّهات النموذج واستدعاءات أدواته. والمقصود بـ RSI هنا هو التحسين الذاتي التكراري على مستوى الـ harness: يحسّن نفسه من تشغيلاته هو، وكل دورة تبدأ من الـ harness الذي خلّفته الدورة السابقة.
</details>

<details>
<summary><strong>هل هذا "تكراري" حقًّا، أم مجرد harness يتعلم القواعد؟</strong></summary>

التكرار هنا ملموس، وهو موجود في الكود. كل جلسة جديدة تركّب كل ما في المكتبة، فالكواشف تراقب harness قد تغيّر بالفعل. وإذا وقعت المشكلة نفسها مرتين في جلسات كان فيها تكييف مركَّب، يحصل النموذج على المصدر الحالي وعلى الأدلة، ويكتب نسخة أشد صرامة؛ وتبقى القديمة محفوظة للرجوع إليها. والمشكلة التي تُصادَف في مساحة عمل ثانية توسّع التكييف ليشمل الجهاز كله. أما ما لا يدخل في التكرار فهو الحَكَم: الكواشف وسياسة التفعيل وبوابة التحقق لا يستطيع أي تكييف أن يغيّرها.
</details>

<details>
<summary><strong>بماذا يختلف هذا عن الـ skills أو ملفات الذاكرة أو موجّه نظام أطول؟</strong></summary>

تلك تضيف نصًّا قد يتبعه النموذج وقد لا يتبعه. أما التكييف فكود على نقاط التوسعة في الـ harness: يستطيع أن يرفض استدعاء أداة قبل تنفيذه، أو يشترط موافقتك، أو يمنع انتهاء الجولة ما دام لم يُتحقَّق من شيء. في التشغيلات المقيسة، ظل النموذج يحاول `python` في 3 جلسات بعد أن قيل له ألا يفعل، ورُفض الاستدعاء قبل تنفيذه.
</details>

<details>
<summary><strong>هل يبطّئ جلساتي؟</strong></summary>

كتابة التكييف تنتظر ردًّا كاملًا واحدًا من النموذج: 30–60 ثانية على `mimo-v2.6-pro`، وتبقى الخطوة متوقفة خلالها. أما التكييفات المركَّبة فتعمل داخل العملية نفسها (in-process) مع مهلات زمنية. لم يُقَس أي تسريع، ولا ندّعي أي تسريع.
</details>

<details>
<summary><strong>هل يمكن لتكييف كتبه النموذج أن يفعل شيئًا خطيرًا؟</strong></summary>

الفئة التلقائية لا تستطيع أن تسمح بشيء كان الـ harness سيرفضه، والقدرات القوية تنتظر موافقتك. الكود يعمل في سياق `node:vm` خاص به خلف جسر JSON. هذا يحمي من الأخطاء ومن سوء الاستخدام العابر. لكنه **ليس** حدًّا أمنيًّا في وجه الكود الخبيث، فاقرأ ملفات `.dsh-rsi/` في المشروع قبل أن تشغّل `dsh-rsi trust`.
</details>

<details>
<summary><strong>مع أي النماذج يعمل؟</strong></summary>

التكييفات يكتبها النموذج الحالي للجلسة، أو النموذج الذي تحدده عبر `provider` و`model`. وإذا عجز النموذج عن إنتاج كود يجتاز البوابة، تتولى القوالب المدمجة المهمة. التشغيلات حتى الآن استخدمت نموذجين من عائلة واحدة: `mimo-v2.6-pro` و`mimo-v2.6-flash`.
</details>

<details>
<summary><strong>هل يعمل في تطبيق سطح المكتب لـ DeepSeek Harness؟</strong></summary>

يُوزَّع بوصفه إضافة عادية من طرف ثالث، ومعه البيانات الوصفية التي تقرؤها صفحات الإضافات، ويُثبَّت في الـ profile `web` الذي يغلّفه التطبيق. لم يُتحقَّق منه بعدُ داخل تطبيق سطح المكتب الحقيقي.
</details>

<details>
<summary><strong>كيف أرى ما تعلّمه، أو أتراجع عنه، أو أوقفه؟</strong></summary>

اكتب `/rsi` داخل الجلسة، أو شغّل `dsh-rsi status` في الطرفية. الأمر `dsh-rsi show <id>` يطبع مصدر التكييف وتقرير التحقق منه؛ و`disable` و`retire` و`rollback` تسحبه أو تعيده إلى ما قبله. واضبط `mode: observe` للتسجيل دون تغيير أي شيء.
</details>

## 🤝 المساهمة والمجتمع

نرحّب بالـ Issues وطلبات الدمج (PRs) على [qybaihe/dshrsi](https://github.com/qybaihe/dshrsi). قبل إرسال PR:

```bash
npm install && npm test    # يشغّل 130 اختبار وحدة، ثم 29 اختبارًا شاملًا؛ دون حاجة إلى أي مفتاح
```

الاختبارات الشاملة تضع مكان نقطة نهاية النموذج (endpoint) نقطةً محاكاة. وكل ما عدا ذلك حقيقي: عملية `dsh`، وتنفيذ الأدوات، وسجل الجلسة، وتثبيت الإضافة.

```
packages/dsh-rsi/        حزمة الإضافة (ESM خالص، بلا خطوة بناء)
  index.js               جانب المضيف: الربط بنقاط التوسعة في DSH
  client.js              جانب المتصفح: شارة RSI وكبسولة الحالة
  src/engine.js          مراقبة ← قرار ← توليد ← تحقق ← تركيب ← حفظ ← مشاركة
  src/signals.js         الكواشف الـ 16
  src/validate.js        بوابة التحقق
  src/sandbox.js         حيث يعمل كود التكييفات
  src/project.js         harness المشروع: <repository>/.dsh-rsi
  bin/rsi.js             الأمر dsh-rsi
market/index.json        فهرس إضافات يمكن إضافته إلى DSH
test/unit/  test/e2e/    اختبارات الوحدة، والاختبارات الشاملة على عملية dsh حقيقية
test/live/               تشغيلات على نموذج حقيقي (تحتاج إلى MIMO_API_KEY)
bench/                   اختبارات الـ benchmark: DSH الأصلي مقابل DSH + dsh-rsi
website/                 الموقع (صفحات ثابتة، بلا خطوة بناء)
```
