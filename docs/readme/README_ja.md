# DSHRSI: DeepSeek Harness のための Recursive Self-Improvement（再帰的自己改善）

### **観察 → 改善 → その上に積み上げる → もう一度。使うほど、あなたのハーネスとして磨かれていく。**

**RSI は Recursive Self-Improvement、つまり再帰的自己改善のことです。DSHRSI は、それを DeepSeek Harness で現実のものにするオープンソースのプラグインです。ハーネスは自分自身の実行を観察し、見つけたトラブルに対処するハーネスのコードをそのセッション自身のモデルに書かせ、そのコードを 5 段階のゲートで検証して、ターンが終わる前にマウントします。そして改善されたハーネスが次のセッションを動かし、さらに改善を重ねます。ファインチューニングはしません。プロンプトを積み上げることもしません。あるのはコードです。計測され、残されるか、書き直されるか、捨てられるコードです。**

<a id="rsi"></a>

## 🔁 RSI = Recursive Self-Improvement（再帰的自己改善）

「rewrite itself（自分を書き換える）」ではありません。**再帰的自己改善**です。システムが自らの能力を使って自らを改善し、改善されたシステムが次のラウンドを担います。3 つの言葉でできていて、DSHRSI はその一つひとつを名乗るに足るものでなければなりません。

| | 求められること | DSHRSI での実現方法 |
| :--- | :--- | :--- |
| **自己（Self）** | 行動する側と変更される側が同じシステムであること | ハーネスがハーネスを変えます。アダプテーションを書くのは、トラブルに遭遇したまさにそのセッションのモデルです。外から調整する人はいません |
| **改善（Improvement）** | 「より良い」が検証できること | すべてのアダプテーションはマウントされる前に 5 段階のゲートを通過し、その後のセッションでも実績を問われます。うまく働くものは昇格し、例外を投げるものは隔離されます |
| **再帰（Recursive）** | あるラウンドの成果が次のラウンドの出発点になること | 次のセッションは改善されたハーネスの上で動き、その状態のまま観察されます。効かなかったアダプテーションは、証拠をもとにより厳しく書き直されます。2 つ目のワークスペースでも必要になったものはマシン全体に広がり、プロジェクトのルールはチームメイト全員のハーネスに届きます |

**4 つのループが入れ子になっています：** ターンの中 → セッションからセッションへ → 改善そのものが改善される → プロジェクトからマシンへ、そしてチームへ。

意図的に再帰に**していない**ものもあります。モデルの重みは決して変わりませんし、検出器、トリガーポリシー、検証ゲートは固定のコードで、どのアダプテーションも触れることができません。自分を変更する部分は、自分では変更できない部分によって検査されます。

<a id="quick-start"></a>

## ⚡ 30 秒クイックスタート

### 1. いつもの作業場所にインストールする
DeepSeek Harness のデスクトップアプリまたは Web UI で **Plugins → Add plugin → Install a third-party plugin** を開き、リリースパッケージの URL を貼り付けて **Install** を選び、続けて **Enable now** を選びます。

```text
https://github.com/qybaihe/dshrsi/releases/download/v0.1.2/dsh-rsi-0.1.2.tgz
```

コマンドラインからもインストールできます。プラグインはプロファイルごとに別々に管理されます。また `dsh plugin add` は `pnpm` を呼び出すため、これが `PATH` 上にある必要があります。

```bash
dsh plugin --profile web add https://github.com/qybaihe/dshrsi/releases/download/v0.1.2/dsh-rsi-0.1.2.tgz
dsh web
```

### 2. あとは普段どおり作業するだけ
設定するものは何もありません。同じトラブルが再発するまで、DSHRSI は表に出てきません。再発すると **RSI** バッジが点灯し、入力欄の下のピルが、ハーネスがたったいま自分を変更したことを知らせます。次のセッションは、最初から改善済みの状態で始まります。

<div align="center">
<img src="../../assets/ui-panel-dark.png" alt="次のセッション：ピルが開き、働いているアダプテーションと、実行前に拒否された呼び出しが一覧表示されている" width="1200" />
</div>

どのセッションでも `/rsi` と入力すれば、何がマウントされているか、それがどのレイヤーに属するか、何があなたの承認を待っているかを確認できます。

`desktop` と `headless` のプロファイル、プラグインインデックス、ローカルの tarball、1 回の実行に限った読み込みについては、[プラグインリファレンス](../../packages/dsh-rsi/README.md#install)で説明しています。

## 🧠 DSHRSI の仕組み：ハーネスの中で何度も回る閉ループ

<div align="center">
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="../../assets/pit-stop.dark.svg" />
  <img src="../../assets/pit-stop.svg" alt="DSHRSI の仕組みをピットストップに見立てた図：マシンがハーネス、ドライバーがモデル、新しいパーツはターンの途中で書かれたハーネスのコード" width="960" />
</picture>
</div>

スキル、メモリファイル、より長いシステムプロンプトは、どれもコンテキストのレベルで働きます。テキストを足して、モデルが従ってくれることを期待するわけです。従わなかったときは、次のセッションでも同じ失敗する呼び出しが繰り返されます。

**DSHRSI はハーネスのレベルで働きます。学んだことは、ハーネス自身の拡張ポイント上のコードになります。**

| ステージ | 仕組み | 効果 |
| :--- | :--- | :--- |
| **1. 観察** | 16 個の検出器が、正規化されたセッションイベントを読みます。再び失敗する呼び出し、何度も現れる失敗原因、迷走、ユーザーによる訂正、何も検証しないまま終わるターンなどです。 | トラブルに、セッションが変わっても同じままのシグネチャが付きます。 |
| **2. 書き換え** | セッション自身のモデルが、10 個のケイパビリティからなる API に対して JavaScript のアダプテーションを書きます。却下されたコードは理由とともに差し戻されますが、それも最大 2 回までで、その後は組み込みテンプレートが引き継ぎます。 | 修正はハーネスのコードであって、プロンプトにもう一段落足すことではありません。 |
| **3. 検証** | 静的検査 → ロード → リプレイ → リグレッション → 権限。アダプテーションは、自分を発動させた呼び出しに対して実際に作用しなければならず、このセッションで成功した呼び出しには一切手を出してはなりません。 | 何もしないコードや、すでに動いていたものを壊すコードは、決してマウントされません。 |
| **4. マウント** | アダプテーションは隔離された専用のコンテキストで動き、すべての呼び出しにタイムアウトが付き、次のモデルリクエストの前に有効になります。 | トラブルに遭遇したそのターンが、最初に恩恵を受けます。 |
| **5. 保持と共有** | マシンごとに、アダプテーションのライブラリがあります。うまく働くものは昇格し、例外を投げるものは隔離され、効かなかったものはより厳しく書き直され、プロジェクトのルールはリポジトリに書き出されます。 | 次のセッションは適応済みの状態で始まり、チームメイトは受け入れを済ませた時点でプロジェクトのルールを受け取ります。 |
| **↻ もう一度** | 次のセッションはステージ 5 が残したハーネスの上で動き、ステージ 1 はすべてのアダプテーションが入った状態でそれを観察します。 | 改善の上に改善が積み上がります。これが再帰です。 |

## 🔬 実際のモデルでの実測

以下の数値は、実際のモデル `mimo-v2.6-pro` を実際の `dsh` セッションで動かして得たものです（`npm run test:live`）。この表にシミュレーションによる値は一つもありません。

> **この表の読み方：** サンプルは小さいです。モデルは 1 つ、シナリオは 3 つ、それぞれ数セッションずつです。示しているのは、このループが端から端まで動くということです。成功率についての統計的な主張では**ありません**し、何かが速くなったわけでもありません。アダプテーションを書くには、モデルの応答を 30–60 秒待つことになります。より大規模な実行は[ベンチマーク](#benchmarks)にあります。

| シナリオ | DSHRSI なし | DSHRSI あり | ハーネスが書いたもの |
| :--- | :--- | :--- | :--- |
| **コマンドがない**：手順には `python` とあるが、マシンには `python3` しかない | ❌ **5 / 5** セッションで失敗する呼び出しが発生 | ✅ アダプテーション適用後は **0 / 7** セッション（適用前は 9 / 9） | `deny` + `prompt`。モデルが書き、1 回目の試行でゲートを通過 |
| **ユーザーが一度だけ伝えたルール**：あるファイルは絶対に変更せず、代わりにその下書きに書くこと | ❌ 次のセッションがそのファイルを編集した | ✅ 次のセッションは何も言われなくても下書きに書いた | `deny` + `prompt`。訂正の直後にモデルが書いた |
| **誰も検証を頼んでいない修正** | 未実行 | ⚪ 何も書かれなかった：モデルは 3 / 3 セッションで自分の修正を検証したため、学ぶことがなかった | なし |

<a id="coverage"></a>

## 🛡️ 検出器とケイパビリティ

**16 個の検出器**が、ハーネスをいつ変えるべきかを判断します。[完全な一覧](../../packages/dsh-rsi/README.md#detectors)はプラグインリファレンスにあります。

**10 個のケイパビリティ**が、アダプテーションにできることのすべてです。アダプテーションは、これらを通じてのみハーネスに触れられます。

| ケイパビリティ | できること | ティア |
| :--- | :--- | :---: |
| `annotate` | ツールの結果に注記を追記する | ✅ 自動 |
| `steer` | 次のモデルリクエストの前に注記を加える | ✅ 自動 |
| `deny` | ツール呼び出しを拒否し、理由を伝える | ✅ 自動 |
| `ask` | 呼び出しにユーザーの承認を要求する | ✅ 自動 |
| `block` | ツールの結果を、訂正内容を伴うエラーに変える | ✅ 自動 |
| `verify` | 条件が満たされないあいだ、ターンを終了させない | ✅ 自動 |
| `prompt` | システムプロンプトに常設のセクションを追加する | ✅ 自動 |
| `rewrite` | ツールの結果のテキストを置き換える | 🔐 要承認 |
| `tool` | モデル向けに新しいツールを登録する | 🔐 要承認 |
| `exec` | ハーネスのシェルツール経由で、同じサンドボックスと承認ルールのもとでコマンドを実行する | 🔐 要承認 |

上の 1 つ目のシナリオでモデルが書いたアダプテーションがこちらです。

```js
define({
  title: 'Route python invocations to python3',
  description: '...',
  capabilities: ['deny', 'prompt'],
  setup(h) {
    h.promptSection('On this machine there is no `python` executable; use `python3`.')
    h.beforeTool({ tool: 'bash', command: /(^|[;&|(]\s*)python(\s|$)/ },
      () => h.deny('`python` is not installed on this machine. Use `python3` instead.'))
  },
})
```

<a id="project-harness"></a>

## 🧩 3 つのレイヤーと、プロジェクトごとのハーネス

すべてのアダプテーションは、3 つのレイヤーのいずれかに属します。レイヤーはそれぞれ個別にオフにできます。

| レイヤー | 保持するもの | 例 | 適用範囲 |
| :--- | :--- | :--- | :--- |
| **`machine`** | このコンピューターについての事実 | `python` がない、ポートが使われている、社内ホストの名前解決ができない | それを学んだワークスペース。2 つ目のワークスペースでも遭遇すれば、マシン全体 |
| **`user`** | あなたがどう扱われたいか | 「長すぎる」という理由で低評価を付けた返信 | マシン全体 |
| **`project`** | 1 つのリポジトリのルールと慣習 | 「このリポジトリでは必ず pnpm を使う」 | ワークスペース、およびリポジトリそのもの：ルールはコードと一緒にコミットされます |

**プロジェクトレイヤーは、コードと一緒に移動します。**

- **コミットすれば共有、削除すれば取り外し**。1 つのファイルが 1 つのアダプテーションです。
- **クローンしただけでは何も実行されません**。各マシンが `dsh-rsi trust` でファイルの内容そのものを受け入れ、内容が変われば改めて受け入れます。
- **プロジェクトにできるのは、ハーネスをより保守的にすることだけ**で、緩めることはできません。`autonomy` のような設定は、プロジェクトからは手が届きません。
- **リポジトリの外へも持ち運べます**。`dsh-rsi export` と `dsh-rsi import` で、マシンレイヤーとユーザーレイヤーを 1 つのファイルとして別のコンピューターへ運べます。

<a id="security"></a>

## 🔒 安全性と設定のデフォルト

- **自動ティアは厳しくする方向のみ** — あなたの承認がなければ、アダプテーションにできるのは、情報を加える、拒否する、確認を求める、検証を要求する、のいずれかだけです。その `deny` と `ask` は、ほかのポリシーが出した判定をより厳しくすることしかできません。
- **強力な操作には承認が必要（`autonomy: tighten`）** — 結果を書き換える、ツールを追加する、コマンドを実行するアダプテーションは `proposed` として保存され、`dsh-rsi approve <id>` を待ちます。
- **必要になるまで見えない** — フリクションがなく、何もマウントされていなければ、システムプロンプト、ツール一覧、メッセージはバイト単位でまったく変わりません。これはエンドツーエンドテストで守られています。
- **障害は封じ込める** — ハンドラーが例外を投げても、それが取り付けられているツール呼び出しには決して影響しません。エラーが 3 回起きると、そのアダプテーションは隔離されます。
- **すべてを記録に残す** — すべての判断、フリクション、マウント、アクションがログに残ります。`dsh-rsi disable`、`retire`、`rollback` で、アダプテーションを外したり元に戻したりできます。
- **3 つのモード** — `adapt` は直接マウントし（デフォルト）、`propose` は生成したうえであなたを待ち、`observe` は記録だけを行います。

<a id="faq"></a>

## ❓ よくある質問

<details>
<summary><strong>DSHRSI はモデルをファインチューニングしたり、変更したりしますか？</strong></summary>

いいえ。モデルの重みには触れず、学習も一切行いません。変わるのはハーネス、つまりモデルのプロンプトとツール呼び出しを取り巻いて動くコードです。ここでいう RSI は、ハーネスのレベルでの再帰的自己改善（Recursive Self-Improvement）です。ハーネスは自分自身の実行から自分を改善し、どのラウンドも前のラウンドが残したハーネスから始まります。
</details>

<details>
<summary><strong>本当に「再帰的」なのですか？ ルールを覚えるだけのハーネスではありませんか？</strong></summary>

再帰は具体的なもので、コードの中にあります。新しいセッションはライブラリにあるものをすべてマウントするので、検出器が観察するのは、すでに変化したハーネスです。アダプテーションがマウントされていたセッションで同じトラブルが 2 回起きると、モデルは現在のソースと証拠を受け取り、より厳しいバージョンを書きます。古いバージョンはロールバック用に残されます。2 つ目のワークスペースでトラブルに遭遇すると、アダプテーションはマシン全体に広がります。再帰しないのは審判役です。検出器、トリガーポリシー、検証ゲートは、どのアダプテーションからも変更できません。
</details>

<details>
<summary><strong>スキルやメモリファイル、長いシステムプロンプトとは何が違うのですか？</strong></summary>

それらはテキストを足すもので、モデルは従うかもしれませんし、従わないかもしれません。アダプテーションは、ハーネスの拡張ポイント上のコードです。ツール呼び出しを実行前に拒否したり、あなたの承認を必須にしたり、何も検証されていないあいだはターンを終わらせないようにしたりできます。実測では、モデルはやめるように伝えられた後も 3 セッションで `python` を試み、その呼び出しは実行前に拒否されました。
</details>

<details>
<summary><strong>セッションは遅くなりますか？</strong></summary>

アダプテーションを書くときは、モデルの応答をまるごと 1 回分待ちます。`mimo-v2.6-pro` では 30–60 秒で、そのあいだそのステップは止まったままです。マウントされたアダプテーションは、タイムアウト付きでプロセス内で動きます。高速化は計測されておらず、主張もしていません。
</details>

<details>
<summary><strong>モデルが書いたアダプテーションが危険なことをする可能性はありますか？</strong></summary>

自動ティアは、ハーネスが拒否するはずのものを何一つ許可できず、強力なケイパビリティはあなたの承認を待ちます。コードは JSON ブリッジを隔てた専用の `node:vm` コンテキストで動きます。これは誤りや軽い気持ちでの誤用に備えるものです。悪意のあるコードに対するセキュリティ境界では**ありません**。ですから、`dsh-rsi trust` を実行する前に、プロジェクトの `.dsh-rsi/` のファイルを読んでください。
</details>

<details>
<summary><strong>どのモデルで動きますか？</strong></summary>

アダプテーションを書くのは、セッションの現在のモデルか、`provider` と `model` で指定したモデルです。モデルがゲートを通過するコードを出せない場合は、組み込みテンプレートが引き継ぎます。これまでの実行で使ったのは、同じファミリーの 2 つのモデル、`mimo-v2.6-pro` と `mimo-v2.6-flash` です。
</details>

<details>
<summary><strong>DeepSeek Harness のデスクトップアプリで動きますか？</strong></summary>

プラグインページが読み取るメタデータを備えた通常のサードパーティプラグインとして配布されており、アプリがラップしている `web` プロファイルにインストールされます。実際のデスクトップアプリの中での検証は、まだできていません。
</details>

<details>
<summary><strong>学習した内容を確認したり、取り消したり、オフにしたりするには？</strong></summary>

セッション内では `/rsi`、ターミナルでは `dsh-rsi status` を使います。`dsh-rsi show <id>` はアダプテーションのソースと検証レポートを表示し、`disable`、`retire`、`rollback` で外したり元に戻したりできます。何も変更せずに記録だけしたい場合は、`mode: observe` を設定します。
</details>
