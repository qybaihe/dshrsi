<a id="rsi"></a>

## 🔁 RSI = Recursive Self-Improvement (การปรับปรุงตนเองแบบเรียกซ้ำ)

ไม่ใช่ "rewrite itself" (เขียนตัวเองใหม่) แต่คือ **การปรับปรุงตนเองแบบเรียกซ้ำ**: ระบบใช้ความสามารถของตัวเองมาปรับปรุงตัวเอง แล้วระบบที่ปรับปรุงแล้วก็เป็นผู้ลงมือทำรอบถัดไป สามคำ และ DSHRSI ต้องทำให้ได้จริงทุกคำ:

| | ต้องมีอะไร | DSHRSI ทำอย่างไร |
| :--- | :--- | :--- |
| **ตนเอง (Self)** | ผู้ลงมือกับสิ่งที่ถูกเปลี่ยนคือระบบเดียวกัน | harness เป็นผู้เปลี่ยน harness เอง ตัว adaptation เขียนโดยโมเดลของเซสชันที่เจอปัญหานั้นเอง ไม่มีใครมาปรับจูนจากภายนอก |
| **ปรับปรุง (Improvement)** | คำว่า "ดีขึ้น" ต้องตรวจสอบได้ | ทุก adaptation ต้องผ่านด่านตรวจสอบ 5 ขั้นก่อนถูก mount และเซสชันหลังจากนั้นก็ยังถูกใช้ตัดสินมันต่อ: ตัวที่ได้ผลถูกเลื่อนขั้น ตัวที่ throw error ถูกกักกัน |
| **เรียกซ้ำ (Recursive)** | ผลลัพธ์ของรอบหนึ่งคือจุดเริ่มต้นของรอบถัดไป | เซสชันถัดไปรันบน harness ที่ปรับปรุงแล้ว และถูกสังเกตบน harness ตัวนั้นด้วย ส่วน adaptation ที่เอาไม่อยู่จะถูกเขียนใหม่ให้เข้มขึ้นตามหลักฐาน ตัวที่จำเป็นใน workspace ที่สองจะขยายขอบเขตไปทั้งเครื่อง และกฎของโปรเจกต์ก็เดินทางไปถึง harness ของเพื่อนร่วมทีมทุกคน |

**สี่ลูป แต่ละลูปซ้อนอยู่ในลูปถัดไป:** ภายในเทิร์นเดียว → จากเซสชันสู่เซสชัน → ตัวการปรับปรุงเองก็ถูกปรับปรุง → จากโปรเจกต์ สู่เครื่อง สู่ทีม

สิ่งที่ตั้งใจให้ **ไม่** เรียกซ้ำ: weights ของโมเดลไม่เคยเปลี่ยน และตัวตรวจจับ นโยบายการ trigger กับด่านตรวจสอบ ล้วนเป็นโค้ดตายตัวที่ไม่มี adaptation ใดแตะต้องได้ ส่วนที่แก้ไขตัวเองได้ ถูกตรวจโดยส่วนที่มันแก้ไขไม่ได้

<a id="quick-start"></a>

## ⚡ เริ่มต้นใช้งานใน 30 วินาที

### 1. ติดตั้งในที่ที่คุณทำงานอยู่แล้ว
ในแอปเดสก์ท็อปหรือ Web UI ของ DeepSeek Harness ให้เปิด **Plugins → Add plugin → Install a third-party plugin** วางลิงก์ของแพ็กเกจ release เลือก **Install** แล้วเลือก **Enable now**:

```text
https://github.com/qybaihe/dshrsi/releases/download/v0.1.3/dsh-rsi-0.1.3.tgz
```

หรือจะใช้ command line ก็ได้ แต่ละ profile เก็บ plugin ของตัวเองแยกกัน และ `dsh plugin add` จะเรียก `pnpm` ซึ่งต้องอยู่ใน `PATH`:

```bash
dsh plugin --profile web add https://github.com/qybaihe/dshrsi/releases/download/v0.1.3/dsh-rsi-0.1.3.tgz
dsh web
```

### 2. ทำงานไปตามปกติ
ไม่ต้องตั้งค่าอะไรเลย DSHRSI จะไม่โผล่มาให้เห็นจนกว่าปัญหาเดิมจะกลับมา เมื่อถึงตอนนั้นป้าย **RSI** จะสว่างขึ้น แถบ pill ใต้ช่องพิมพ์ข้อความจะบอกคุณว่า harness เพิ่งเปลี่ยนตัวเองไป และเซสชันถัดไปก็เริ่มต้นในสภาพที่ปรับปรุงแล้ว:

<div align="center">
<img src="../../assets/ui-panel-dark.png" alt="เซสชันถัดไป: แถบ pill ถูกกางออก แสดง adaptation ที่กำลังทำงานอยู่ และการเรียกที่มันปฏิเสธไปก่อนจะถูกรัน" width="1200" />

พิมพ์ `/rsi` ในเซสชันใดก็ได้ เพื่อดูว่ามีอะไร mount อยู่บ้าง แต่ละตัวอยู่ในเลเยอร์ไหน และมีอะไรรอการอนุมัติจากคุณ

ส่วน profile `desktop` และ `headless`, plugin index, tarball ในเครื่อง และการโหลดเฉพาะการรันครั้งเดียว ดูได้ใน[เอกสารอ้างอิงของ plugin](../../packages/dsh-rsi/README.md#install)

## 🧠 DSHRSI ทำงานอย่างไร: ลูปปิดภายใน harness ที่วนซ้ำแล้วซ้ำอีก

<div align="center">
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="../../assets/pit-stop.dark.svg" />
  <img src="../../assets/pit-stop.svg" alt="การทำงานของ DSHRSI วาดเป็นการเข้าพิต: รถคือ harness นักขับคือโมเดล และชิ้นส่วนใหม่คือโค้ดของ harness ที่เขียนขึ้นกลางเทิร์น" width="960" />
</picture>
</div>

Skill, ไฟล์ memory และ system prompt ที่ยาวขึ้น ล้วนทำงานในระดับ context: เพิ่มข้อความเข้าไปแล้วหวังว่าโมเดลจะทำตาม เมื่อโมเดลไม่ทำตาม การเรียกที่ล้มเหลวแบบเดิมก็เกิดขึ้นอีกในเซสชันถัดไป

**DSHRSI ทำงานในระดับ harness สิ่งที่มันเรียนรู้จะกลายเป็นโค้ดบน extension point ของ harness เอง:**

| ขั้นตอน | กลไก | ผลลัพธ์ |
| :--- | :--- | :--- |
| **1. สังเกต** | ตัวตรวจจับ 16 ตัวอ่าน event ของเซสชันที่ผ่านการ normalize แล้ว: การเรียกที่ล้มเหลวซ้ำ สาเหตุของความล้มเหลวที่วนกลับมาเรื่อย ๆ การลองคำสั่งแบบสะเปะสะปะ การทักแก้จากผู้ใช้ และเทิร์นที่จบลงโดยไม่ได้ตรวจสอบอะไรเลย | ปัญหาได้ signature ที่คงเดิมจากเซสชันหนึ่งไปยังเซสชันถัดไป |
| **2. เขียนใหม่** | โมเดลของเซสชันนั้นเองเขียน adaptation เป็น JavaScript ตาม API ที่มี 10 ความสามารถ โค้ดที่ไม่ผ่านจะถูกส่งกลับพร้อมเหตุผล ไม่เกินสองครั้ง จากนั้น template ที่มีมาในตัวจะเข้ามารับช่วงแทน | วิธีแก้คือโค้ด harness ไม่ใช่ prompt ที่งอกเพิ่มอีกหนึ่งย่อหน้า |
| **3. ตรวจสอบ** | ตรวจตามลำดับ static → load → replay → regression → permission โดย adaptation ต้องมีผลกับการเรียกที่ trigger มัน และต้องไม่แตะการเรียกใดเลยที่สำเร็จในเซสชันนี้ | โค้ดที่ไม่ทำอะไรเลย หรือทำให้ของที่เคยใช้ได้พัง จะไม่มีวันถูก mount |
| **4. Mount** | adaptation รันใน context ของตัวเองที่ถูกแยกส่วนไว้ มี timeout กำกับทุกการเรียก และมีผลก่อน request ถัดไปที่ส่งถึงโมเดล | เทิร์นที่เจอปัญหาคือเทิร์นแรกที่ได้ประโยชน์ |
| **5. เก็บและแชร์** | แต่ละเครื่องมีคลัง adaptation ของตัวเอง ตัวที่ได้ผลถูกเลื่อนขั้น ตัวที่ throw error ถูกกักกัน ตัวที่เอาไม่อยู่ถูกเขียนใหม่ให้เข้มขึ้น และกฎของโปรเจกต์ถูกเขียนลงใน repository | เซสชันถัดไปเริ่มต้นแบบปรับตัวมาแล้ว และเพื่อนร่วมทีมได้กฎของโปรเจกต์เมื่อยอมรับกฎเหล่านั้นแล้ว |
| **↻ วนอีกรอบ** | เซสชันถัดไปรันบน harness ที่ขั้นตอน 5 ทิ้งไว้ให้ และขั้นตอน 1 สังเกตมันโดยมี adaptation ทุกตัวอยู่ครบ | การปรับปรุงต่อยอดบนการปรับปรุง นี่แหละคือการเรียกซ้ำ |

## 🔬 วัดผลกับโมเดลจริง

ตัวเลขเหล่านี้มาจากการรันโมเดลจริง `mimo-v2.6-pro` ผ่านเซสชัน `dsh` จริง (`npm run test:live`) ไม่มีอะไรในตารางนี้ที่เป็นการจำลอง

> **วิธีอ่านตารางนี้:** กลุ่มตัวอย่างมีขนาดเล็ก หนึ่งโมเดล สามสถานการณ์ สถานการณ์ละไม่กี่เซสชัน มันแสดงให้เห็นว่าลูปทำงานได้ครบตั้งแต่ต้นจนจบ แต่ **ไม่ใช่** ข้อสรุปทางสถิติเกี่ยวกับอัตราความสำเร็จ และไม่มีอะไรเร็วขึ้น: การเขียน adaptation หนึ่งตัวต้องรอโมเดล 30–60 วินาที ส่วนการรันชุดใหญ่กว่าอยู่ใน [Benchmark](#benchmarks)

| สถานการณ์ | ไม่มี DSHRSI | มี DSHRSI | สิ่งที่ harness เขียน |
| :--- | :--- | :--- | :--- |
| **คำสั่งที่ไม่มีในเครื่อง**: คำแนะนำเขียนว่า `python` แต่เครื่องมีแค่ `python3` | ❌ **5 / 5** เซสชันเรียกคำสั่งที่ล้มเหลว | ✅ **0 / 7** เซสชันหลังมี adaptation (ก่อนหน้านั้น 9 / 9) | `deny` + `prompt` เขียนโดยโมเดล ผ่านด่านตรวจสอบตั้งแต่ครั้งแรก |
| **กฎที่ผู้ใช้บอกไว้ครั้งเดียว**: ห้ามแก้ไฟล์ไฟล์หนึ่ง ให้เขียนลงฉบับร่างของไฟล์นั้นแทน | ❌ เซสชันถัดไปแก้ไฟล์นั้น | ✅ เซสชันถัดไปเขียนลงฉบับร่างเองโดยไม่ต้องบอก | `deny` + `prompt` เขียนโดยโมเดลทันทีหลังถูกทักแก้ |
| **การแก้ไขที่ไม่มีใครสั่งให้ตรวจสอบ** | ไม่ได้รัน | ⚪ ไม่ได้เขียนอะไร: โมเดลตรวจสอบการแก้ไขของตัวเองใน 3 / 3 เซสชัน จึงไม่มีอะไรให้เรียนรู้ | ไม่มี |

**ความสามารถ 10 อย่าง** คือทั้งหมดที่ adaptation ทำได้ มันเข้าถึง harness ได้ผ่านความสามารถเหล่านี้เท่านั้น:

| ความสามารถ | ทำอะไร | ระดับ |
| :--- | :--- | :---: |
| `annotate` | ต่อท้ายหมายเหตุให้ผลลัพธ์ของ tool | ✅ อัตโนมัติ |
| `steer` | เพิ่มหมายเหตุก่อน request ถัดไปที่ส่งถึงโมเดล | ✅ อัตโนมัติ |
| `deny` | ปฏิเสธ tool call พร้อมบอกเหตุผล | ✅ อัตโนมัติ |
| `ask` | บังคับให้การเรียกต้องได้รับอนุมัติจากผู้ใช้ | ✅ อัตโนมัติ |
| `block` | เปลี่ยนผลลัพธ์ของ tool ให้เป็น error ที่แนบคำแนะนำแก้ไขมาด้วย | ✅ อัตโนมัติ |
| `verify` | ไม่ยอมให้เทิร์นจบตราบใดที่เงื่อนไขยังไม่เป็นจริง | ✅ อัตโนมัติ |
| `prompt` | เพิ่ม section ถาวรเข้าไปใน system prompt | ✅ อัตโนมัติ |
| `rewrite` | แทนที่ข้อความในผลลัพธ์ของ tool | 🔐 ต้องอนุมัติ |
| `tool` | ลงทะเบียน tool ใหม่ให้โมเดล | 🔐 ต้องอนุมัติ |
| `exec` | รันคำสั่งผ่าน shell tool ของ harness ภายใต้กฎ sandbox และกฎการอนุมัติชุดเดียวกัน | 🔐 ต้องอนุมัติ |

นี่คือ adaptation ที่โมเดลเขียนในสถานการณ์แรกข้างต้น:

```js
define({
  title: 'Route python invocations to python3',
  description: '...',
  capabilities: ['deny', 'prompt'],
  setup(h) {
    h.promptSection('On this machine there is no `python` executable; use `python3`.')
    h.beforeTool({ tool: 'bash', command: /(^|[;&|(]\s*)python(\s|$)/ },
      () => h.deny('`python` is not installed on this machine. Use `python3` instead.'))
  },
})
```

## 🧩 สามเลเยอร์ และ harness หนึ่งชุดต่อหนึ่งโปรเจกต์

ทุก adaptation อยู่ในเลเยอร์ใดเลเยอร์หนึ่งจากสามเลเยอร์ แต่ละเลเยอร์ปิดแยกกันได้:

| เลเยอร์ | เก็บอะไร | ตัวอย่าง | มีผลที่ไหน |
| :--- | :--- | :--- | :--- |
| **`machine`** | ข้อเท็จจริงเกี่ยวกับคอมพิวเตอร์เครื่องนี้ | ไม่มี `python`; port ถูกใช้ไปแล้ว; host ภายใน resolve ไม่ได้ | workspace ที่เรียนรู้มันมา จากนั้นขยายไปทั้งเครื่องเมื่อ workspace ที่สองเจอปัญหาเดียวกัน |
| **`user`** | วิธีที่คุณอยากให้มันปฏิบัติต่อคุณ | คำตอบที่ถูกกดว่าไม่ดี พร้อมเหตุผลว่า "ยาวเกินไป" | ทั้งเครื่อง |
| **`project`** | กฎและธรรมเนียมของ repository หนึ่ง | "repository นี้ใช้ pnpm เสมอ" | workspace และตัว repository เอง: กฎถูก commit ไปพร้อมกับโค้ด |

**เลเยอร์ของโปรเจกต์เดินทางไปกับโค้ด:**

- **Commit เพื่อแชร์ ลบเพื่อถอดออก** หนึ่งไฟล์คือหนึ่ง adaptation
- **ไม่มีอะไรรันเพียงเพราะถูก clone มา** แต่ละเครื่องยอมรับเนื้อหาของไฟล์แบบตรงตัวด้วย `dsh-rsi trust` และต้องยอมรับใหม่เมื่อไฟล์เปลี่ยน
- **โปรเจกต์ทำได้แค่ให้ harness ระมัดระวังมากขึ้น** ไม่มีทางน้อยลง การตั้งค่าอย่าง `autonomy` นั้นโปรเจกต์เอื้อมไม่ถึง
- **พกพาได้แม้อยู่นอก repository** `dsh-rsi export` และ `dsh-rsi import` ขนเลเยอร์ของเครื่องและของผู้ใช้ไปยังคอมพิวเตอร์อีกเครื่องในรูปไฟล์เดียว

<a id="security"></a>

## 🔒 ความปลอดภัยและค่าเริ่มต้นของการตั้งค่า

- **ระดับอัตโนมัติเข้มขึ้นได้อย่างเดียว** — หากไม่มีการอนุมัติจากคุณ adaptation ทำได้เพียงเพิ่มข้อมูล ปฏิเสธ ถาม หรือบังคับให้ตรวจสอบ ส่วน `deny` และ `ask` ของมันทำได้เพียงให้คำตัดสินของ policy อื่นเข้มงวดขึ้น
- **ความสามารถที่มีพลังสูงต้องได้รับอนุมัติ (`autonomy: tighten`)** — adaptation ที่เขียนผลลัพธ์ใหม่ เพิ่ม tool หรือรันคำสั่ง จะถูกเก็บไว้ในสถานะ `proposed` และรอ `dsh-rsi approve <id>`
- **มองไม่เห็นจนกว่าจะจำเป็น** — เมื่อไม่มี friction และไม่มีอะไร mount อยู่ ทั้ง system prompt รายการ tool และข้อความ จะไม่เปลี่ยนแม้แต่ไบต์เดียว มี end-to-end test คอยคุมเรื่องนี้อยู่
- **ความล้มเหลวถูกจำกัดวง** — handler ที่ throw error จะไม่กระทบ tool call ที่มันผูกอยู่ด้วยเลย เมื่อ error ครบสามครั้ง adaptation ตัวนั้นจะถูกกักกัน
- **ทุกอย่างมีบันทึก** — ทุกการตัดสินใจ ทุก friction ทุกการ mount และทุก action ถูกบันทึกไว้ คำสั่ง `dsh-rsi disable`, `retire` และ `rollback` ใช้ถอด adaptation ออกหรือย้อนกลับ
- **สามโหมด** — `adapt` mount ทันที (ค่าเริ่มต้น), `propose` สร้างแล้วรอคุณ, `observe` บันทึกอย่างเดียว

<a id="faq"></a>

## ❓ คำถามที่พบบ่อย

<details>
<summary><strong>DSHRSI fine-tune หรือเปลี่ยนแปลงโมเดลหรือไม่?</strong></summary>

ไม่เลย weights ของโมเดลไม่ถูกแตะต้อง และไม่มีการ train อะไรทั้งสิ้น สิ่งที่เปลี่ยนคือ harness: โค้ดที่รันอยู่รอบ ๆ prompt และ tool call ของโมเดล RSI ในที่นี้คือการปรับปรุงตนเองแบบเรียกซ้ำในระดับ harness: มันปรับปรุงตัวเองจากการทำงานของตัวเอง และทุกรอบเริ่มจาก harness ที่รอบก่อนทิ้งไว้
</details>

<details>
<summary><strong>นี่ "เรียกซ้ำ" จริงหรือ หรือเป็นแค่ harness ที่เรียนรู้กฎ?</strong></summary>

การเรียกซ้ำนี้เป็นรูปธรรม และอยู่ในโค้ดจริง เซสชันใหม่จะ mount ทุกอย่างที่คลังมีอยู่ ตัวตรวจจับจึงสังเกต harness ที่เปลี่ยนไปแล้ว เมื่อปัญหาเดิมเกิดขึ้นสองครั้งในเซสชันที่มี adaptation mount อยู่ โมเดลจะได้รับซอร์สโค้ดปัจจุบันพร้อมหลักฐาน แล้วเขียนเวอร์ชันที่เข้มขึ้น โดยเวอร์ชันเก่าถูกเก็บไว้สำหรับ rollback ปัญหาที่เจอใน workspace ที่สองจะขยาย adaptation ไปทั้งเครื่อง สิ่งที่ไม่เรียกซ้ำคือผู้ตัดสิน: ตัวตรวจจับ นโยบายการ trigger และด่านตรวจสอบ ไม่มี adaptation ใดเปลี่ยนได้
</details>

<details>
<summary><strong>ต่างจาก skill, ไฟล์ memory หรือ system prompt ที่ยาวขึ้นอย่างไร?</strong></summary>

สิ่งเหล่านั้นเพิ่มข้อความที่โมเดลอาจทำตามหรือไม่ทำตามก็ได้ ส่วน adaptation คือโค้ดบน extension point ของ harness: มันสามารถปฏิเสธ tool call ก่อนที่จะรัน บังคับให้ต้องได้รับอนุมัติจากคุณ หรือไม่ยอมให้เทิร์นจบในขณะที่ยังไม่มีอะไรถูกตรวจสอบ ในการรันที่วัดผล โมเดลยังพยายามเรียก `python` ใน 3 เซสชันหลังจากถูกบอกแล้วว่าอย่าใช้ และการเรียกนั้นถูกปฏิเสธก่อนที่จะรัน
</details>

<details>
<summary><strong>มันทำให้เซสชันของฉันช้าลงไหม?</strong></summary>

การเขียน adaptation ต้องรอคำตอบเต็ม ๆ จากโมเดลหนึ่งครั้ง: 30–60 วินาทีบน `mimo-v2.6-pro` ซึ่งระหว่างนั้น step จะหยุดนิ่ง ส่วน adaptation ที่ mount แล้วจะรันภายใน process เดียวกันโดยมี timeout กำกับ ไม่มีการวัดพบว่าเร็วขึ้น และเราไม่ได้อ้างว่าเร็วขึ้น
</details>

<details>
<summary><strong>adaptation ที่โมเดลเขียนทำอะไรที่เป็นอันตรายได้ไหม?</strong></summary>

ระดับอัตโนมัติไม่สามารถอนุญาตสิ่งใดที่ harness จะปฏิเสธได้ และความสามารถที่มีพลังสูงต้องรอการอนุมัติจากคุณ โค้ดรันใน context `node:vm` ของตัวเองหลัง JSON bridge ซึ่งกันความผิดพลาดและการใช้ในทางที่ผิดแบบไม่จริงจังได้ แต่ **ไม่ใช่** security boundary สำหรับกันโค้ดที่ประสงค์ร้าย ดังนั้นให้อ่านไฟล์ `.dsh-rsi/` ของโปรเจกต์ก่อนรัน `dsh-rsi trust`
</details>

<details>
<summary><strong>ใช้กับโมเดลไหนได้บ้าง?</strong></summary>

adaptation เขียนโดยโมเดลปัจจุบันของเซสชัน หรือโมเดลที่คุณกำหนดด้วย `provider` และ `model` หากโมเดลเขียนโค้ดที่ผ่านด่านตรวจสอบไม่ได้ template ที่มีมาในตัวจะรับช่วงแทน การรันจนถึงตอนนี้ใช้สองโมเดลจากตระกูลเดียวกัน คือ `mimo-v2.6-pro` และ `mimo-v2.6-flash`
</details>

<details>
<summary><strong>ใช้ในแอปเดสก์ท็อปของ DeepSeek Harness ได้ไหม?</strong></summary>

มันมาในรูป third-party plugin ธรรมดาตัวหนึ่ง พร้อม metadata ที่หน้า plugin อ่าน และติดตั้งลงใน profile `web` ที่แอปครอบอยู่ แต่ยังไม่ได้ตรวจสอบภายในแอปเดสก์ท็อปจริง
</details>

<details>
<summary><strong>ถ้าการปรับปรุงกลายเป็นว่าผิดจะเกิดอะไรขึ้น?</strong></summary>

ย้อนกลับได้เสมอ: โค้ดของ harness เองไม่เคยถูกแตะต้อง และไม่มีเวอร์ชันใดของ adaptation ถูกลบทิ้งเลย harness จะถอยกลับเองเมื่อ adaptation ล้มเหลวซ้ำ ๆ หรือเมื่อการเรียกที่มันปฏิเสธไปกลายเป็นว่าใช้ได้จริง คุณเองก็ทำได้เช่นกัน: `/rsi undo` ย้อนกลับการเปลี่ยนแปลงล่าสุด `dsh-rsi restore` นำ harness ทั้งชุดกลับไปยังจุดใดจุดหนึ่งก่อนหน้านี้ และ `/rsi off` รัน harness ตัวมาตรฐาน ทั้งหมดนี้มีผลในเซสชันที่กำลังรันอยู่แล้ว [การย้อนกลับทำงานอย่างไร](../../packages/dsh-rsi/README.md#going-back)
</details>

<details>
<summary><strong>จะดู ยกเลิก หรือปิดสิ่งที่มันเรียนรู้ได้อย่างไร?</strong></summary>

ใช้ `/rsi` ในเซสชัน หรือ `dsh-rsi status` ใน terminal ส่วน `dsh-rsi show <id>` จะพิมพ์ซอร์สโค้ดและรายงานการตรวจสอบของ adaptation ออกมา และ `disable`, `retire`, `rollback` ใช้ถอดมันออกหรือย้อนกลับ ตั้ง `mode: observe` เพื่อบันทึกอย่างเดียวโดยไม่เปลี่ยนอะไร
</details>
