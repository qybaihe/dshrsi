# DSHRSI: рекурсивное самосовершенствование (Recursive Self-Improvement) для DeepSeek Harness

### **Наблюдает → улучшает → строит поверх улучшенного → и снова. Харнесс, который раз за разом становится всё более вашим.**

<img src="../../assets/rsi-trace.gif" alt="Анимация по записи реального прогона: на стандартном харнессе 12 сессий из 30 делают один и тот же неудачный вызов; с DSHRSI харнесс на третий раз улучшает сам себя, и в следующих 22 сессиях это случается один раз" width="960" />

**RSI — это Recursive Self-Improvement, рекурсивное самосовершенствование, а DSHRSI — open-source-плагин, который делает его реальностью для DeepSeek Harness. Харнесс наблюдает за собственными запусками, поручает модели той же сессии написать код харнесса под найденную проблему, прогоняет этот код через 5-этапный гейт валидации и монтирует его до конца хода. Затем следующую сессию ведёт уже улучшенный харнесс — и улучшается снова. Никакого файнтюнинга. Никакой груды промптов. Только код, который измеряют, оставляют, переписывают или выбрасывают.**

### 🔴 Без DSHRSI
Каждая сессия заново открывает одни и те же факты: на этой машине нет `python`, в этом репозитории действует правило, которое вы уже озвучили, это исправление никто не проверял. ### 🧬 С DSHRSI
Когда проблема возвращается, модель пишет фрагмент кода харнесса, он проходит гейт и начинает работать **на том же ходу**. В 3 прогонах на реальной модели **7 сессий из 7** после адаптации обошлись без неудачных вызовов. А следующее улучшение стартует уже с этой точки.

<a id="rsi"></a>

## 🔁 RSI = Recursive Self-Improvement, рекурсивное самосовершенствование

Не «rewrite itself», не «переписать себя». **Recursive Self-Improvement**, рекурсивное самосовершенствование: система улучшает себя собственными силами, а следующий раунд выполняет уже улучшенная система. Три слова, и каждое DSHRSI обязан заслужить:

| | Что для этого нужно | Как это делает DSHRSI |
| :--- | :--- | :--- |
| **Self** (сам себя) | Действует и изменяется одна и та же система | Харнесс меняет харнесс. Адаптацию пишет модель той самой сессии, которая наткнулась на проблему. Никто не подкручивает его снаружи |
| **Improvement** (совершенствование) | «Лучше» должно быть проверяемым | Каждая адаптация перед монтированием проходит 5-этапный гейт, а последующие сессии проверяют её на деле: что работает — получает повышение, что бросает исключения — уходит в карантин |
| **Recursive** (рекурсивно) | Результат одного раунда — старт следующего | Следующая сессия идёт на улучшенном харнессе, на нём же за ней и наблюдают. Адаптация, которая не удержала проблему, переписывается строже — по собранным свидетельствам. Та, что понадобилась во второй рабочей области, расширяется на всю машину, а правила проекта доезжают до харнесса каждого коллеги |

**Четыре цикла, каждый внутри следующего:** внутри хода → от сессии к сессии → улучшается само улучшение → от проекта к машине и к команде.

Что намеренно **не** рекурсивно: веса модели не меняются никогда, а детекторы, политика срабатывания и гейт валидации — это фиксированный код, до которого не дотянется ни одна адаптация. Ту часть, что изменяет себя, проверяет часть, которую она изменить не может.

<a id="quick-start"></a>

## ⚡ Быстрый старт за 30 секунд

### 1. Установите там, где уже работаете
В десктопном приложении DeepSeek Harness или в веб-интерфейсе откройте **Plugins → Add plugin → Install a third-party plugin**, вставьте ссылку на релизный пакет, нажмите **Install**, затем **Enable now**:

```text
https://github.com/qybaihe/dshrsi/releases/download/v0.1.0/dsh-rsi-0.1.0.tgz
```

Или из командной строки. У каждого профиля свой набор плагинов, а `dsh plugin add` вызывает `pnpm`, который должен быть в `PATH`:

```bash
dsh plugin --profile web add https://github.com/qybaihe/dshrsi/releases/download/v0.1.0/dsh-rsi-0.1.0.tgz
dsh web
```

### 2. Просто работайте
Настраивать нечего. DSHRSI остаётся в тени, пока та же проблема не повторится. Тогда загорается бейдж **RSI**, плашка под полем ввода сообщает, что харнесс только что изменил себя, а следующая сессия стартует уже улучшенной:

<div align="center">
<img src="../../assets/ui-panel-dark.png" alt="Следующая сессия: плашка раскрыта и показывает работающую адаптацию и вызов, который она отклонила ещё до запуска" width="1200" />
</div>

Наберите `/rsi` в любой сессии, чтобы увидеть, что смонтировано, к какому слою оно относится и что ждёт вашего одобрения.

### 3. Дайте репозиторию собственный харнесс
Правила, усвоенные в репозитории, могут жить в самом репозитории — по одному файлу на адаптацию:

```bash
# Команда поставляется вместе с плагином, внутри профиля, в который он установлен
alias dsh-rsi="$HOME/.dsh/profiles/web/node_modules/.bin/dsh-rsi"

dsh-rsi project init      # в репозитории: создаёт .dsh-rsi/, после чего закоммитьте его
dsh-rsi trust             # на каждой другой машине: примите файлы, прочитав их
```

### 4. Запуск из исходников

```bash
git clone https://github.com/qybaihe/dshrsi.git && cd dshrsi
npm install               # подтягивает зафиксированную версию dsh и pnpm, который тот вызывает
npx dsh plugin --profile web add "$PWD/packages/dsh-rsi"
npx dsh web
```

Профили `desktop` и `headless`, индексы плагинов, локальные tar-архивы и загрузка на один запуск описаны в [справочнике по плагину](../../packages/dsh-rsi/README.md#install).

<a id="how-it-works"></a>

## 🧠 Как работает DSHRSI: замкнутый цикл внутри харнесса, раз за разом

Скиллы, файлы памяти и всё более длинные системные промпты работают на уровне контекста: добавляют текст и надеются, что модель ему последует. Когда она не следует, тот же неудачный вызов повторяется в следующей сессии.

**DSHRSI работает на уровне харнесса. То, чему он научился, становится кодом на собственных точках расширения харнесса:**

```mermaid
flowchart LR
  subgraph S1["1 · Наблюдение"]
    A["события сессии"] --> B["16 детекторов"]
  end
  subgraph S2["2 · Решение"]
    B --> C["сигнатура трения<br/>+ библиотека + прошлые сессии"]
  end
  subgraph S3["3 · Переписывание"]
    C --> D["модель сессии<br/>пишет адаптацию"]
    D --> E["5-этапный гейт валидации"]
    E -. "отклонено, с причинами" .-> D
  end
  subgraph S4["4 · Монтирование"]
    E --> F["изолированный контекст node:vm<br/>работает уже до следующего запроса к модели"]
  end
  subgraph S5["5 · Сохранение и распространение"]
    F --> G["библиотека: повышение · карантин · пересмотр"]
    G --> H[".dsh-rsi/ в репозитории"]
  end
  G -. "следующая сессия начинается отсюда" .-> A
```

| Этап | Механизм | Эффект |
| :--- | :--- | :--- |
| **1. Наблюдение** | 16 детекторов читают нормализованные события сессии: вызовы, которые падают повторно, причины сбоев, которые возвращаются снова и снова, метания, поправки пользователя, ходы, которые заканчиваются без единой проверки. | Проблема получает сигнатуру, стабильную от сессии к сессии, например `bash:command-not-found:python`. |
| **2. Переписывание** | Модель самой сессии пишет адаптацию на JavaScript поверх API из 10 возможностей. Отклонённый код возвращается с причинами, не более двух раз, после чего в дело вступает встроенный шаблон. | Исправление — это код харнесса, а не ещё один абзац промпта. |
| **3. Валидация** | Статика → загрузка → воспроизведение → регрессия → права. Адаптация обязана сработать на тех вызовах, из-за которых она появилась, и не должна трогать ни один вызов, который в этой сессии прошёл успешно. | Код, который ничего не делает или ломает то, что уже работало, не монтируется никогда. |
| **4. Монтирование** | Адаптация работает в собственном контексте `node:vm` за JSON-мостом, с таймаутом на каждый вызов, и вступает в силу до следующего запроса к модели. | Первым выигрывает тот самый ход, который наткнулся на проблему. |
| **5. Сохранение и распространение** | Библиотека на каждой машине — с реестром и журналом аудита. Что работает — получает повышение, что бросает исключения — уходит в карантин, что не удержало проблему — переписывается строже, а правила проекта записываются в `.dsh-rsi/`. | Следующая сессия стартует уже адаптированной, а коллеги получают правила проекта после `dsh-rsi trust`. |
| **↻ И снова** | Следующая сессия идёт на харнессе, который остался после этапа 5, а этап 1 наблюдает за ней уже со всеми адаптациями на месте. | Улучшение строится на улучшении. Это и есть рекурсия. |

## 🔬 Замеры на реальной модели

Эти цифры получены на реальной модели `mimo-v2.6-pro` в реальных сессиях `dsh` (`npm run test:live`). В этой таблице нет ничего симулированного.

> **Как это читать:** выборка маленькая. Одна модель, три сценария, по несколько сессий на каждый. Она показывает, что цикл работает от начала до конца. Это **не** статистическое утверждение о доле успехов, и быстрее ничего не стало: написание адаптации — это 30–60 секунд ожидания модели. Прогоны покрупнее — в разделе [Бенчмарки](#benchmarks).

| Сценарий | Без DSHRSI | С DSHRSI | Что написал харнесс |
| :--- | :--- | :--- | :--- |
| **Отсутствующая команда**: в README написано `python stats.py`, а на машине есть только `python3` | ❌ **5 / 5** сессий сделали неудачный вызов | ✅ **0 / 7** сессий после адаптации (9 / 9 до неё) | `deny` + `prompt`, написано моделью, прошло гейт с первой попытки |
| **Правило, которое пользователь озвучил один раз**: «никогда не изменяй `notes.txt`, пиши в `notes.draft.txt`» | ❌ Следующая сессия отредактировала `notes.txt` | ✅ Следующая сессия без напоминаний писала в `notes.draft.txt` | `deny` + `prompt`, написано моделью сразу после поправки |
| **Исправление, которое никто не просил проверить** | не запускалось | ⚪ Ничего не написано: модель проверила своё исправление в 3 / 3 сессий, так что учиться было нечему | нет |

Первый сценарий прогонялся с плагином трижды, каждый раз с пустой библиотеки, плюс один контрольный прогон. Второй — один раз с плагином и один раз без него.

| **С DSHRSI · прогон 2** | ❌ 1 | ❌ 1 | ❌ 1 → 🧬 | ✅ 0 | ✅ 0 | |

Самый большой прирост — +7 (MBPP+ с `mimo-v2.6-flash`), самая большая потеря — −3 (MBPP с `mimo-v2.6-pro`), и ни одно различие не выдерживает точного теста Макнемара на одних и тех же задачах (наименьшее p = 0.17). **А вот что DSHRSI действительно сделал, причём без единой подсказки, — изменил сам себя.** За восемь прогонов модели написали **56 адаптаций**; 15 из них сработали, а 10 из этих сработавших были расширены на всю машину. | Остальные 8 | | измеримых изменений нет | | |

Ни одна из этих двух не добавила решённых задач, а плагин обошёлся примерно в 8–9% дополнительного времени агента и входных токенов. Все десять перечислены в [`bench/README.md`](../../bench/README.md#did-those-adaptations-work).

**LiveCodeBench v6 оборвался раньше времени:** на аккаунте модели посреди прогона закончился баланс. На задачах, которые к этому моменту успели завершить обе стороны, стоковый DSH решил 94, а DSHRSI — 96 из 105 с `mimo-v2.6-pro`, и 42 против 42 из 51 с `mimo-v2.6-flash`. ## 🛡️ Детекторы и возможности

**16 детекторов** решают, когда харнессу пора меняться. Одни и те же детекторы работают и на живой сессии, и на сессии, сохранённой на диске (`dsh-rsi mine`):

| Детектор | Что находит | Реакция |
| :--- | :--- | :---: |
| `repeat-failing-call` | Тот же вызов снова падает с теми же аргументами | адаптация |
| `failure-signature` | Одна и та же причина сбоя возвращается снова и снова: нет команды, нет зависимости, сеть, права доступа, порт занят, путь не найден, несовпадение при правке, неверные аргументы, нехватка памяти | адаптация |
| `command-flailing` | Команды одного типа падают подряд с меняющимися аргументами | адаптация |
| `read-thrash` | Один и тот же неизменившийся файл читается снова и снова | адаптация |
| `edit-churn` | Один и тот же файл правится много раз за один ход | адаптация |
| `error-storm` | Большинство недавних вызовов инструментов завершились ошибкой | адаптация |
| `stall` | Сбои подряд, без единого успеха между ними | адаптация |
| `timeout-recurrence` | Команды одного типа раз за разом упираются в таймаут | адаптация |
| `output-flood` | Команды одного типа раз за разом выдают слишком большой вывод | адаптация |
| `approval-denied` / `denied-repeat` | Пользователь раз за разом отклоняет действия одного типа, или отклонённый вызов повторяется без изменений | адаптация |
| `user-correction` | Пользователь поправил модель или прервал её и сменил направление | адаптация |
| `premature-completion` | Код изменён, а ход вот-вот закончится без единой запущенной проверки | адаптация |
| `negative-feedback` | Пользователь отметил ответ как плохой и написал причину | адаптация |
| `user-interrupt` | Пользователь прервал ход на середине | запись |
| `model-instability` | Запросы к модели раз за разом падают, повторяются или упираются в лимит вывода | запись |
| `context-pressure` | Контекст был сжат посреди задачи | запись |

**10 возможностей** — это всё, что умеет адаптация. До харнесса она дотягивается только через них:

| Возможность | Что делает | Уровень |
| :--- | :--- | :---: |
| `annotate` | Дописывает примечание к результату инструмента | ✅ автоматический |
| `steer` | Добавляет примечание перед следующим запросом к модели | ✅ автоматический |
| `deny` | Отклоняет вызов инструмента и называет причину | ✅ автоматический |
| `ask` | Требует одобрения пользователя для вызова | ✅ автоматический |
| `block` | Превращает результат инструмента в ошибку, которая несёт поправку | ✅ автоматический |
| `verify` | Не даёт ходу завершиться, пока не выполнено условие | ✅ автоматический |
| `prompt` | Добавляет постоянный раздел в системный промпт | ✅ автоматический |
| `rewrite` | Заменяет текст результата инструмента | 🔐 требует одобрения |
| `tool` | Регистрирует новый инструмент для модели | 🔐 требует одобрения |
| `exec` | Запускает команду через shell-инструмент харнесса, с теми же правилами песочницы и одобрения | 🔐 требует одобрения |

Вот адаптация, которую модель написала в первом сценарии выше:

```js
define({
  title: 'Route python invocations to python3',
  description: '...',
  capabilities: ['deny', 'prompt'],
  setup(h) {
    h.promptSection('On this machine there is no `python` executable; use `python3`.')
    h.beforeTool({ tool: 'bash', command: /(^|[;&|(]\s*)python(\s|$)/ },
      () => h.deny('`python` is not installed on this machine. Use `python3` instead.'))
  },
})
```

## 🧩 Три слоя и свой харнесс у каждого проекта

Каждая адаптация принадлежит одному из трёх слоёв. Любой слой можно отключить отдельно от остальных:

| Слой | Что в нём хранится | Пример | Где действует |
| :--- | :--- | :--- | :--- |
| **`machine`** | Факты об этом компьютере | Нет `python`; порт занят; внутренний хост не резолвится | Рабочая область, где это было усвоено, а затем вся машина, как только на то же наткнётся вторая рабочая область |
| **`user`** | Как вы хотите, чтобы с вами обращались | Ответ, отмеченный как плохой, с причиной «слишком длинно» | Вся машина |
| **`project`** | Правила и привычки одного репозитория | «В этом репозитории используется pnpm, всегда» | Рабочая область, а через `.dsh-rsi/` — и сам репозиторий |

**Слой проекта путешествует вместе с кодом:**

```
.dsh-rsi/
  harness.json           маркер формата и настройки уровня проекта
  adaptations/
    remember-the-user-s-instruction-3f2a1c.js     усвоено, затем записано сюда
    no-force-push.js                              написанная вручную работает точно так же
```

- **Закоммитьте, чтобы поделиться; удалите, чтобы отключить.** Один файл — одна адаптация.
- **Ничто не запускается только потому, что его склонировали.** Каждая машина принимает точное содержимое файлов командой `dsh-rsi trust` и принимает их заново, когда они меняются.
- **Проект может сделать харнесс только консервативнее**, но не наоборот. Настройки вроде `autonomy` проекту недоступны.
- **Переносимо и за пределами репозитория.** `dsh-rsi export` и `dsh-rsi import` переносят слои машины и пользователя на другой компьютер одним файлом.

<a id="security"></a>

## 🔒 Безопасность и настройки по умолчанию

- **Автоматический уровень только ужесточает** — без вашего одобрения адаптация может лишь добавить информацию, отклонить, спросить или потребовать проверки. Её `deny` и `ask` могут сделать вердикт остальных политик только строже.
- **Мощные возможности — только с одобрения (`autonomy: tighten`)** — адаптации, которые переписывают результаты, добавляют инструменты или запускают команды, сохраняются как `proposed` и ждут `dsh-rsi approve <id>`.
- **Невидим, пока не понадобится** — пока нет трения и ничего не смонтировано, системный промпт, список инструментов и сообщения остаются неизменными байт в байт. За этим следит сквозной тест.
- **Сбои изолированы** — обработчик, бросивший исключение, никогда не влияет на вызов инструмента, к которому он привязан. После трёх ошибок адаптация уходит в карантин.
- **Всё под запись** — каждое решение попадает в `audit.jsonl`, каждое трение, монтирование и срабатывание — в `ledger.jsonl`. `dsh-rsi disable`, `retire` и `rollback` убирают адаптацию или откатывают её назад.
- **Три режима** — `adapt` монтирует сразу (по умолчанию), `propose` генерирует и ждёт вас, `observe` только записывает.

<a id="faq"></a>

## ❓ Частые вопросы

<details>
<summary><strong>DSHRSI делает файнтюнинг или изменяет модель?</strong></summary>

Нет. Веса модели не затрагиваются, ничего не обучается. Меняется харнесс: код, который работает вокруг промптов модели и вызовов инструментов. RSI здесь — это рекурсивное самосовершенствование на уровне харнесса: он улучшает себя на основе собственных запусков, и каждый раунд начинается с харнесса, который остался после предыдущего.
</details>

<details>
<summary><strong>Это действительно «рекурсия» или просто харнесс, который заучивает правила?</strong></summary>

Рекурсия конкретна, и она в коде. Новая сессия монтирует всё, что хранится в библиотеке, поэтому детекторы наблюдают за харнессом, который уже изменился. Когда та же проблема дважды возникает в сессиях, где адаптация была смонтирована, модель получает текущий исходник и свидетельства и пишет более строгую версию; старая сохраняется для отката. Проблема, встреченная во второй рабочей области, расширяет адаптацию на всю машину. Не рекурсивен только судья: детекторы, политику срабатывания и гейт валидации не может изменить ни одна адаптация.
</details>

<details>
<summary><strong>Чем это отличается от скиллов, файлов памяти или более длинного системного промпта?</strong></summary>

Они добавляют текст, которому модель может последовать, а может и нет. Адаптация — это код на точках расширения харнесса: он может отклонить вызов инструмента до запуска, потребовать вашего одобрения или не дать ходу завершиться, пока ничего не проверено. В замерах модель всё равно пыталась вызвать `python` в 3 сессиях после того, как ей сказали этого не делать, и вызов отклонялся ещё до запуска.
</details>

<details>
<summary><strong>Замедляет ли он мои сессии?</strong></summary>

Написание адаптации — это ожидание одного полного ответа модели: 30–60 секунд на `mimo-v2.6-pro`, и всё это время шаг стоит на месте. Смонтированные адаптации работают внутри процесса, с таймаутами. Ускорения замеры не показали, и мы о нём не заявляем.
</details>

<details>
<summary><strong>Может ли адаптация, написанная моделью, сделать что-то опасное?</strong></summary>

Автоматический уровень не может разрешить ничего из того, что харнесс отклонил бы, а мощные возможности ждут вашего одобрения. Код работает в собственном контексте `node:vm` за JSON-мостом. Это защищает от ошибок и небрежного использования. Это **не** граница безопасности против вредоносного кода, поэтому прочитайте файлы `.dsh-rsi/` проекта, прежде чем запускать `dsh-rsi trust`.
</details>

<details>
<summary><strong>С какими моделями он работает?</strong></summary>

Адаптации пишет текущая модель сессии или та, которую вы зададите через `provider` и `model`. Если модель не может выдать код, проходящий гейт, в дело вступают встроенные шаблоны. Пока что прогоны проводились на двух моделях одного семейства: `mimo-v2.6-pro` и `mimo-v2.6-flash`.
</details>

<details>
<summary><strong>Работает ли он в десктопном приложении DeepSeek Harness?</strong></summary>

Он поставляется как обычный сторонний плагин с метаданными, которые читают страницы плагинов, и устанавливается в профиль `web`, который приложение оборачивает. В реальном десктопном приложении он пока не проверялся.
</details>

<details>
<summary><strong>Как посмотреть, отменить или отключить то, чему он научился?</strong></summary>

`/rsi` в сессии или `dsh-rsi status` в терминале. `dsh-rsi show <id>` выводит исходник адаптации и отчёт о валидации; `disable`, `retire` и `rollback` убирают её или откатывают назад. Задайте `mode: observe`, чтобы только записывать и ничего не менять.
</details>
